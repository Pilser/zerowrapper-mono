# Topcoat Asset Bundle — How It Works

## What assets are

Assets are static files the browser needs: CSS (tailwind output) and JS modules
(`main.js`, `owner.js`, the chat JS files). They are declared in Rust with the
`asset!` macro:

```rust
use topcoat::asset::asset;
// in layout.rs:
<script type="module" src=(asset!("assets/js/chat/main.js"))></script>
```

The CSS is generated by the Tailwind build script and referenced via:

```rust
<link rel="stylesheet" href=(topcoat::tailwind::stylesheet!())>
```

## Two-phase design (this is the key)

`asset!` does **NOT** embed the file bytes into the binary. It only embeds a
2048-byte **declaration record** per asset: an `AssetId` (FNV-1a hash of
`crate_name + source_file + path + options`) plus the path string.

So the binary knows *which* files it needs, but does not contain them.

## Bundle generation

After `cargo build`, run:

```sh
topcoat asset bundle --bin zw --release --out <OUT_DIR>
```

What it does:
1. Rebuilds (or reuses) the binary for the given profile.
2. Scans the binary bytes for the `TOPCOAT_ASSET` markers.
3. Reads each asset's path, copies the file from the crate's `assets/` dir.
4. Writes each file with a content-hash filename: `main-<sha256[:16]>.js`.
5. Writes `manifest.toml` mapping each `AssetId` → filename + hash + content_type.

**CRITICAL:** the profile must match the deployed binary. A bundle generated
from the debug build has different `AssetId`s than the release build (the
tailwind stylesheet ID differs). The container panics with
`failed to resolve asset ... in the asset catalog` when they mismatch.

Use `--release` when the deployed binary is a release build.

## Runtime loading

`load_assets()` in `app.rs`:

1. `AssetBundle::load()` — walks up from the exe dir looking for
   `assets/manifest.toml` (auto-detect).
2. Fallback: `TOPCOAT_ASSETS_DIR` env var → `AssetBundle::load_dir(path)`.
3. Fallback: temporary dir with an empty `manifest.toml` (so the server never
   crashes, just serves no assets).

Served URLs: `/_topcoat/assets/<filename>`.

## Deployment for pilserlabs

```
cargo build --release
topcoat asset bundle --bin zw --release --out /home/vox/pilserlabs/pilserlabs/assets/
cp target/release/zw /home/vox/pilserlabs/pilserlabs/zw
docker compose -f wrapper/compose.yml --env-file wrapper/pilserlabs.env up -d zw
```

The `assets/` dir (bundle + YAML configs) is mounted into the container at
`/app/config` and found via `TOPCOAT_ASSETS_DIR=/app/config`.

## YAML configs are NOT assets

`landing.yaml` and `sitesettings.yaml` are runtime config read by `serde_yaml`
in `main.rs`. They live next to the bundle but are loaded from disk, not from
the asset catalog. Paths come from `ZEROWRAPPER_LANDING_YAML` and
`ZEROWRAPPER_SETTINGS_YAML`.
